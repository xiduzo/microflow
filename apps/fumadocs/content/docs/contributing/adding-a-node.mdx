title: Add a new node
description: Walkthrough for adding a brand-new node to Microflow Studio — runtime, frontend, and registry.
---

Adding a node touches three places: the **runtime** (Rust, where it executes), the **frontend** (React, where the user configures it), and the **registry** (a JSON file that stitches the two together). This page walks you through each.

You should already have the dev environment running — see [Build from source](/docs/contributing/build-from-source).

## The big picture

```
node-components.json              ← single source of truth (UI ↔ runtime mapping)
        │
        ├── frontend (React + Zod schema)        — apps/web/src/nodes/<name>/
        │     ├── <name>.tsx              UI component
        │     ├── <name>.schema.ts        Zod schema for data + value, and the defaults
        │     └── <name>.adapter.ts       optional host adapter (no React)
        │
        └── runtime (Rust)                       — crates/microflow-core/src/nodes/<name>/
              ├── mod.rs                  lists the layers below, each behind its feature gate
              ├── config.rs               the node's settings, shared by runtime and codegen
              ├── runtime.rs              implements the Component trait
              └── codegen.rs              optional Arduino sketch emitter
```

The two sides never call each other directly — they communicate through the Yjs document and the runtime event channel.

You never register a node in TypeScript by hand. `bun run codegen` reads `node-components.json` and writes the node type list, the node catalog and the React node map into `apps/web/src/nodes/*.generated.ts` (Step 5).

For this walkthrough, we will add a hypothetical `Sparkle` node that emits a random number between two bounds whenever it receives an input.

## Step 1 — Pick a group

The Add Node panel sorts nodes into groups: **sense**, **generate**, **shape**, **decide**, **express**, or **internal**. You set the group in the node's `defaults` (Step 3). The group is a label only. It does not decide where any code lives: the Rust code of every node goes in its own folder, whatever its group.

`Sparkle` transforms an input into an output, so it is a **shape** node.

## Step 2 — Write the runtime node (Rust)

The runtime lives in the `microflow-core` crate. The desktop app runs it natively, and the web app runs the same code compiled to WebAssembly. Each node has one folder, `crates/microflow-core/src/nodes/<name>/`, named in snake_case (`RangeMap` lives in `nodes/range_map/`). `nodes/smooth/` is a short working example to keep open next to this step.

### The module file

Create `crates/microflow-core/src/nodes/sparkle/mod.rs`:

```rust
//! The `Sparkle` node.

pub mod config;
#[cfg(feature = "runtime")]
pub mod runtime;
```

This file lists the layers the node has, and puts each one behind its feature gate. `config` has no gate, because the Arduino export reads it too. `runtime` sits behind the `runtime` feature. A node that uses a network service or a host peripheral (`Mqtt`, `Llm`, `Figma`, `Midi`, `Music`) puts its runtime behind `cloud` instead.

### The config

Create `crates/microflow-core/src/nodes/sparkle/config.rs`:

```rust
//! Sparkle Node config — shared by the live runtime and the codegen emitter.

use serde::{Deserialize, Serialize};

#[derive(Debug, Clone, Serialize, Deserialize)]
#[serde(rename_all = "camelCase", default)]
pub struct SparkleConfig {
    pub min: f64,
    pub max: f64,
}

impl Default for SparkleConfig {
    fn default() -> Self {
        Self { min: 0.0, max: 100.0 }
    }
}
```

The runtime deserializes the node's `data` into this struct. Keep `rename_all = "camelCase"`: the frontend sends `windowSize`, not `window_size`, and without the attribute a multi-word field never matches and silently keeps its default. `default` fills in the fields that `data` does not have, so keep these defaults equal to the Zod defaults of Step 3.

### The component

Create `crates/microflow-core/src/nodes/sparkle/runtime.rs`:

```rust
//! Sparkle Component — emits a random number between two bounds.

use crate::runtime::{
    Component, ComponentBase, ComponentBuilder, ComponentValue, RuntimeContext, RuntimeError,
};

pub use super::config::SparkleConfig;

pub struct Sparkle {
    base: ComponentBase,
    config: SparkleConfig,
}

impl Sparkle {
    #[must_use]
    pub fn new(id: String, config: SparkleConfig) -> Self {
        Self {
            base: ComponentBase::new(id, ComponentValue::Number(0.0)),
            config,
        }
    }
}

impl Component for Sparkle {
    fn ports() -> &'static [&'static str] {
        &["trigger"]
    }

    fn emits() -> &'static [&'static str] {
        &[ComponentBase::VALUE_HANDLE]
    }

    fn base(&self) -> &ComponentBase {
        &self.base
    }
    fn base_mut(&mut self) -> &mut ComponentBase {
        &mut self.base
    }
    fn component_type(&self) -> &'static str {
        "Sparkle"
    }

    fn dispatch(
        &mut self,
        method: &str,
        _args: ComponentValue,
        ctx: &mut RuntimeContext,
    ) -> Result<(), RuntimeError> {
        match method {
            "trigger" => {
                // microflow-core has no `rand` (it builds for wasm32): hash the
                // host clock instead, like `nodes/oscillator/runtime.rs` does.
                let r = ((ctx.now_ms() * 12.9898).sin() * 43758.5453).fract().abs();
                let SparkleConfig { min, max } = self.config;
                self.base.set_value(ComponentValue::Number(min + r * (max - min)));
                Ok(())
            }
            _ => Err(RuntimeError::ComponentError(format!("Unknown method: {method}"))),
        }
    }
}

impl ComponentBuilder for Sparkle {
    type Config = SparkleConfig;
    fn build(id: String, config: Self::Config) -> Result<Self, RuntimeError> {
        Ok(Self::new(id, config))
    }
}
```

- `ports()` lists the input handles and `emits()` the output handles. They are the only place you declare them: Step 5 copies them to the frontend, where they become the node's handles.
- The runtime calls `dispatch` once for each value that arrives on a port, with the port name as `method`.
- `self.base.set_value(…)` stores the value and, when it changed, emits it on the `value` handle (`ComponentBase::VALUE_HANDLE`). To emit on another handle, call `self.base.emit_with_value(…)` and list the handle in `emits()`. `nodes/range_map/runtime.rs` does this for its `to` handle.
- A node has no thread, clock or timer of its own. `ctx` gives it the host clock (`ctx.now_ms()`) and timers: `ctx.schedule_wakeup(…)` calls the node back through `dispatch_internal`, as `nodes/delay/runtime.rs` does.
- A node that uses the board also implements `HardwareComponent` and returns `Some(self)` from `as_hardware_mut`. See `nodes/led/runtime.rs`.

### Register it

Node registration is explicit. Make three one-line edits in `crates/microflow-core/src/`:

1. In `nodes/mod.rs`, add `pub mod sparkle;`.
2. In `runtime/registry.rs`, add the node to `register_all`. The string is the node's name in `node-components.json` (Step 5). A `cloud` node goes in the `#[cfg(feature = "cloud")]` block.

   ```rust
   self.register::<nodes::sparkle::runtime::Sparkle>("Sparkle");
   ```

3. In `codegen/parity.rs`, add the node to `classify`. Every registered node needs an arm there, or the parity test `every_registered_node_type_is_classified` fails. Sparkle has no Arduino emitter, so it gets an exemption:

   ```rust
   "Sparkle" => Exempt("no Arduino emitter yet — falls through to the placeholder comment"),
   ```

### Arduino export (optional)

Studio can export a flow as an Arduino sketch. A node takes part only if it has a `codegen.rs`. Without one, the sketch has a `// unsupported Node …` comment in its place. To add an emitter:

1. Create `nodes/sparkle/codegen.rs` and add `pub mod codegen;` (no feature gate) to `nodes/sparkle/mod.rs`. Read the settings through `super::config::SparkleConfig`, so the sketch uses the same fields and defaults as the runtime. `nodes/smooth/codegen.rs` shows the shape: an `emit` function and a `value_var` that names the C++ variable with the node's output.
2. In `codegen/mod.rs`, add an arm to `emit_node` (the node's C++) and one to `output_expression` (the C++ expression that each emit handle stands for).
3. In `codegen/parity.rs`, replace the `Exempt` arm with a `Case`: a test that feeds inputs to the emitter and checks that the C++ does what `runtime.rs` does.
4. If the node owns a pin, add it to the pin checks in `codegen/validate.rs`.

## Step 3 — Define the frontend schema

The node's folder and files use the kebab-case of its name (`RangeMap` lives in `range-map/range-map.schema.ts`). Code generation imports them by that path.

Create `apps/web/src/nodes/sparkle/sparkle.schema.ts`:

```ts
import { z } from "zod";
import { baseDataSchema } from "../_base/_base.schema";

export const valueSchema = z.number();
export type Value = z.infer<typeof valueSchema>;

export const dataSchema = baseDataSchema.extend({
  instance: z.literal("Sparkle").default("Sparkle"),
  min: z.number().default(0),
  max: z.number().default(100),
});
export type Data = z.infer<typeof dataSchema>;

export const defaults = {
  ...dataSchema.parse({}),
  group: "shape",
  tags: ["value"],
  label: "Sparkle",
  description: "Emit a random number between two bounds",
  icon: "SparklesIcon",
};
```

`baseDataSchema` includes the fields every node has (`label`, `instance`, etc.). You only declare the new ones.

The schema file must export `dataSchema` and `defaults` under exactly those names. `defaults` is the data a new Sparkle starts with, plus what the Add Node panel shows: `group` picks the section, `icon` is the name of a [lucide](https://lucide.dev/icons) icon as `lucide-react` exports it (`SparklesIcon`), and `tags` and `description` feed the search.

## Step 4 — Build the React node

Create `apps/web/src/nodes/sparkle/sparkle.tsx`:

```tsx
import { NodeContainer, useNodeControls, useNodeData, type BaseNode } from "../_base/_base";
import { NodeHandles } from "../_base/node-handles";
import { useNodeValue } from "@/nodes/live/node-data";
import { type Data, type Value, defaults } from "./sparkle.schema";

export function Sparkle(props: Props) {
  return (
    <NodeContainer {...props}>
      <Value />
      <Settings />
      <NodeHandles instance="Sparkle" />
    </NodeContainer>
  );
}

function Value() {
  const value = useNodeValue<Value>(0);
  return <div>{value.toFixed(1)}</div>;
}

function Settings() {
  const data = useNodeData<Data>();
  const { render } = useNodeControls({
    min: { value: data.min, label: "Min" },
    max: { value: data.max, label: "Max" },
  });
  return <>{render()}</>;
}

type Props = BaseNode<Data>;
Sparkle.defaultProps = { data: defaults };
```

Export the component under the node's name (`Sparkle`, not `SparkleNode`): the generated React node map imports it by that name.

`NodeHandles` draws one handle per port and emit that the Rust component declares, so the handles always match the runtime. `useNodeValue(fallback)` returns the node's live value from the runtime, or `fallback` until the first one arrives.

Match an existing nearby node (e.g. `apps/web/src/nodes/calculate/`) for the exact import paths and hook signatures — they evolve.

## Step 5 — Register it and run codegen

Open `apps/web/node-components.json` and add two entries:

```json
{
  "entries": [
    /* ... existing entries ... */
    {
      "name": "Sparkle",
      "impl": "Sparkle"
    }
  ],
  "impls": [
    /* ... existing impls ... */
    {
      "name": "Sparkle",
      "category": "transformation",
      "requiresHardware": false
    }
  ]
}
```

- `entries[].name` is the node's name. It must match the string in `register_all` (Step 2) and the `instance` in the schema (Step 3).
- `entries[].impl` names the `impls` row that the entry runs as. Most nodes point at themselves. Variants share one: `Force` runs as `Sensor`.
- `impls[].category` is a label (`input`, `output`, `control`, `generator`, `transformation`, or `external`). No file path or Rust module follows from it.
- `requiresHardware` tells Studio that the node does nothing without a board.

Then, from `apps/web`, run:

```sh
bun run catalog:sync
```

This does two things:

1. It reads the ports and emits the Rust component declares and writes them to `apps/web/wire-interface.generated.json`. On the way, it checks that `register_all` and `entries[]` list the same names: a name in only one of them fails the command.
2. It runs `bun run codegen`, which writes three files in `apps/web/src/nodes/`:
   - `component-types.generated.ts`: the list of node types, with their ports and emits.
   - `catalog.generated.ts`: the schema, defaults and host adapter of every node, without React.
   - `node-types.generated.ts`: the React component of every node, for the canvas.

Do not edit the generated files by hand. When you change only the frontend or the JSON, and not the Rust ports or emits, `bun run codegen` is enough.

## Step 6 — Add a host adapter (optional)

Most nodes skip this step. A node needs a host adapter when the app itself must act on the node's config. For example, `Hotkey` registers its keyboard shortcut, and `Mqtt` tells the runtime which broker it uses.

Create `apps/web/src/nodes/sparkle/sparkle.adapter.ts` and export an `adapter` of type `NodeHostAdapter` (see `apps/web/src/nodes/_base/host-adapter.ts` for the hooks you can implement). If Sparkle had a keyboard shortcut in its data, the adapter would be:

```ts
import type { NodeHostAdapter } from "../_base/host-adapter";

export const adapter: NodeHostAdapter = {
  accelerator: (node) => (node.data?.accelerator ? String(node.data.accelerator) : undefined),
};
```

Codegen finds the file by its name, so run `bun run codegen` after you add or remove it. Keep it free of React: non-UI code loads the adapter through the catalog. `apps/web/src/nodes/hotkey/hotkey.adapter.ts` and `apps/web/src/nodes/mqtt/mqtt.adapter.ts` are working examples.

## Step 7 — Verify

From the repository root, run the Rust checks:

```sh
cargo test -p microflow-core --features cloud
cargo test --manifest-path apps/web/src-tauri/Cargo.toml
cargo clippy --workspace --all-targets -- -D warnings -W clippy::pedantic
```

The first command runs the runtime tests and the parity test from Step 2. `runtime` and `cloud` are not default features of `microflow-core`: without `--features cloud`, it builds no runtime code and runs none of its tests. The second runs the catalog check from Step 5. CI runs the same Clippy command.

Then, from `apps/web`, run the TypeScript checks:

```sh
bun run check-types
bun test
```

Then start Studio:

```sh
bun run dev:web
```

Open Studio. Open the Add Node panel. Drag a Sparkle node onto the canvas. Connect a [Trigger](/docs/microflow-studio/nodes/generate/trigger) to its input and a [Monitor](/docs/microflow-studio/nodes/internal/monitor) to its output. Press the trigger — the Monitor should show a fresh random value each time.

## Step 8 — Check it works in the browser too

Studio runs in two hosts: the desktop app (native Rust runtime) and the web app
(the same runtime compiled to WebAssembly). Every node is registered in both —
so if your node needs nothing but the runtime, it already works in both.

It does **not** work in both if it depends on something the browser sandbox does
not hand out: an OS-level keyboard hook, a native peripheral, a raw TCP socket, a
request to an endpoint that does not send CORS headers.

If that is your node, add a row to
`apps/web/src/nodes/_base/browser-support.ts`:

```ts
const BROWSER_LIMITATIONS: Record<string, () => string | undefined> = {
  Sparkle: () => "Sparkle needs an OS-level sparkle bus. Use the desktop app.",
};
```

A row makes a **desktop only** badge appear on the node header and beside the
node in the Add Node list, with your text as its tooltip — no change to your node
component, and every instance picks it up.

Return `undefined` from the row when the browser at hand *can* do the job (the
`Midi` row does this: Web MIDI exists in Chromium, not in Firefox or Safari).
Nodes that drive a pin need no row at all — `requiresHardware` in
`node-components.json` already marks them, and the browser flags them when Web
Serial is missing.

A limitation that depends on the node's *config* rather than the node type —
"this broker URL is not reachable from a browser" — belongs next to that
config's other checks instead. See `mqtt.tsx` (the node) and
`routes/configuration/mqtt.tsx` (the broker form).

Before you add a row, make sure the limitation is real. Most "desktop-only"
behaviour is not the runtime — the same Rust engine runs in both hosts — but a
missing bit of host wiring, and wiring it up is usually the smaller change.

## Step 9 — Document it

Add a reference page at `apps/fumadocs/content/docs/microflow-studio/nodes/shape/sparkle.mdx`. Match the template used by neighbouring node pages — see the [docs style guide](/docs/contributing/docs-style-guide) for the canonical structure.

Add `"sparkle"` to `apps/fumadocs/content/docs/microflow-studio/nodes/shape/meta.json` so it appears in the nav.

## Common pitfalls

- **Zod schema mismatch with the Rust config.** If the frontend sends `min` and `SparkleConfig` calls the field `lower`, `lower` silently keeps its default (without `default`, the runtime refuses to build the node instead). Match field names exactly, and keep `rename_all = "camelCase"` on the config so multi-word fields match too.
- **Forgetting `node-components.json`.** Without it the node will not appear in the Add Node panel even if everything else is correct, and `bun run catalog:sync` fails because `register_all` names a node that the catalog does not have.
- **Reaching for `rand`, threads or `sleep` in a node.** `microflow-core` also builds for WebAssembly. Use `ctx.now_ms()` for time and `ctx.schedule_wakeup(…)` for timers (Step 2).
- **Names that do not match.** For every entry, codegen imports the component `Sparkle` from `sparkle/sparkle.tsx`, and `dataSchema` and `defaults` from `sparkle/sparkle.schema.ts`. A different folder, file or export name shows up as a type error in a `*.generated.ts` file. Fix the node, not the generated file.
- **Importing from the rest of the app.** `apps/web/src` is split into one folder per domain (`board/`, `runtime/`, `ui/`, …). A node may import only the files that another folder lists as public in `apps/web/scripts/architecture/verticals.ts`. Run `bun test src/architecture.test.ts` in `apps/web` to check your imports.
- **Hardware flag wrong.** If your node touches a pin, `requiresHardware` must be `true` so Studio shows that the node needs a board, and the browser flags it when Web Serial is missing. The runtime does not read the flag: it sets up the board for the components that implement `HardwareComponent` (Step 2).
- **Assuming desktop-only capabilities.** The web app runs the same runtime in WebAssembly. If your node reaches for a native capability, say so in `browser-support.ts` (Step 8) instead of letting it fail silently in the browser.
- **Hot reload does not always pick up schema changes.** Restart `bun run dev:web` after edits to schema files.
