---
title: Documentation style guide
description: Templates and conventions for the Microflow docs.
---

These docs follow the [Diátaxis](https://diataxis.fr/) framework. Every page is a **Tutorial**, a **How-to**, a **Reference**, or an **Explanation**.

To choose a type, ask what the page does: teach, solve a problem, list facts, or explain. Then use the matching template below.

## File layout

```
apps/fumadocs/content/docs/
├── learn/                  Tutorials  (learning-oriented)
├── how-to/                 How-to     (problem-oriented)
├── microflow-studio/       Reference  (info-oriented, Studio)
├── microflow-hardware-bridge/  Reference (info-oriented, Bridge)
├── concepts/               Explanation (understanding-oriented)
├── troubleshooting/        How-to (symptom-oriented)
└── contributing/           Mixed (project meta)
```

Every directory needs a `meta.json` that lists pages in nav order:

```json
{
  "title": "Section title",
  "pages": ["index", "page-a", "page-b"]
}
```

Every page needs frontmatter:

```mdx
---
title: Page title
description: One sentence that shows up in cards and search results.
---
```

## Templates by document type

### Tutorial template

Goal: a beginner *learns* by doing. End state: the reader has built or done a working thing.

```mdx
---
title: <verb-led, "Build a thing">
description: <one-sentence promise of the outcome>
---

<one paragraph: what you'll have at the end>

## What you need
<bullet list>

## Step 1 — <action>
<concrete instruction; tell them what to type / drag>

## Step 2 — <action>
...

## What just happened?
<short conceptual debrief — connect to bigger picture>

## Next up
→ <link to next tutorial>
```

Use `Step N — Verb` headings. Promise success at every step.

### How-to template

Goal: a competent reader needs to *get something done*.

```mdx
---
title: <verb-led, "Do specific thing">
description: <one-sentence problem statement and approach>
---

<one paragraph: what this guide solves and when to use it>

## When you need it
<symptoms — bullet list>

## Steps
1. <action>
2. <action>
3. <verify>

## Verify it worked
<a check the reader can run>

## Related
- <link to reference>
- <link to concept>
```

Skip explanation; assume background knowledge. Be terse.

### Reference template (node pages)

Goal: a reader needs to *look up an answer about a specific node*.

```mdx
---
title: <NodeName>
description: <one-sentence: what the node does>
---

<one paragraph: what the node is for, with example use cases>

## Inputs
<bullet list of input handles, what they accept>

## Outputs
<bullet list of output handles, what they emit>

## Settings
- **Setting name** — what it does, accepted values, default

## Wiring
<table OR diagram: only if hardware is involved>

## Tips
<short notes about pitfalls; optional>

## Resources
<links to upstream protocol docs / external references>
```

Order matters: Inputs, Outputs, Settings, Wiring, Tips, Resources. Skip sections that do not apply.

### Concept (explanation) template

Goal: a curious reader wants to *understand*.

```mdx
---
title: <noun phrase>
description: <one-sentence summary of the idea>
---

<opening: framing question or scenario>

## <First subhead>
<prose, ~3 paragraphs>

## <Second subhead>
<prose>

...

## Related
- <links to reference and how-to>
```

Concepts can be longer (1–2 thousand words). Discursive style is fine. The voice is "essay", not "checklist".

### Video script template

Every video in `videos/` has a script before it has a recording. The script is the deliverable; the recording is produced from it.

```mdx
---
title: "Script: <video title>"
description: Shooting script for the <runtime> <subject> video.
---

<Video title="<video title>" duration="<m:ss>" />

## At a glance
<table: goal, audience, runtime, hardware>

## Where it appears
<the doc pages that embed this video>

## Set up before you record
<hardware, wiring, app state, what must be prepared off camera>

## Shot list
<Chapters> … </Chapters>

## Script
### <timecode> — <section>
**Screen:** <what is on screen>
**Narration:**
> "<word for word>"
**On-screen text:** <overlays>

## Deliberate failure
<what breaks on camera, and how it is fixed>

## Post-production notes
<cuts, zooms, captions that need care>
```

Rules:

- **Put narration in quotation marks.** Everything else is a stage direction.
- **Record a deliberate failure** in every script where the task can fail. The reader recognises the error later because they have seen it.
- **Do not cut a wait short** when the wait is the content: a firmware flash, a model thinking, a dead cable.
- **Do not repeat the [production guide](/docs/videos/production-guide).** It holds the capture settings and the publishing checklist.

## Embedding a video in a doc page

Use the `<Video />` component. Without a `src` it renders a placeholder linking to the script, which is how an unrecorded video stays visible to readers:

```mdx
<Video title="Your first flow" duration="3:30" script="/docs/videos/first-flow">
One line describing what the viewer will see.
</Video>
```

When the recording exists, add `src="…"` to the same tag. Nothing else on the page changes.

Every page must read correctly with the video removed. The text is the source of truth. The video demonstrates it.

## Writing rules

Write in Simplified Technical English. The rules below are not style preferences. They exist to remove ambiguity.

### Sentences

- **One instruction per sentence.** Two actions means two sentences, or two numbered steps.
- **Keep instructions under 20 words.** Keep descriptions under 25.
- **Use the imperative for instructions.** "Open the settings", not "you can open the settings" or "the settings can be opened".
- **Use the present tense.** "The node emits a value", not "the node will emit a value".
- **Use the active voice.** Name who does the thing.

### Words

- **One word for one thing.** The **Add node** palette is always the **Add node** palette. Never "the node menu", "the palette", or "the picker".
- **Name UI elements exactly as they are labelled.** Copy the label from the app.
- **Replace a pronoun with its noun** when more than one noun could be meant. "Open the node. The node shows its pin." not "Open it. It shows its pin."
- **Delete hedges.** No "simply", "just", "basically", "of course", "obviously", "actually", "in practice".
- **Delete flourishes.** No jokes, no idioms, no rhetorical questions, no "the trick is", no "worse than not working".
- **Use the definite article.** "Press the button", not "press button".
- **Do not stack nouns.** Three-word noun clusters at most.

### Structure

- **Put the warning before the step it applies to**, never after.
- **State a condition before the action.** "If the status shows an error, unplug the board." not "Unplug the board if the status shows an error."
- **Give every procedure a verify step.** Say what the reader should see.
- **Order troubleshooting causes by frequency**, most common first, and say so.

### What to cut

Cut a paragraph if it does one of these:

- Restates the heading.
- Explains why the docs are organised the way they are.
- Tells the reader how to feel about the product.
- Repeats something the next section says better.

## Code samples

- Make every sample syntactically correct and copy-pasteable.
- Tag the fence `sh` for shell, `ts` for TypeScript, `rust` for Rust.
- Use realistic example values such as `light_level`. Never `foo` or `bar`.

## Cross-linking

Link every page three ways:

- **Up** — to the section index, such as `/docs/learn`.
- **Across** — to at least one sibling page, under **Related**.
- **Down** — to the reference page for every node you name.

Link a node like this: `[NodeName](/docs/microflow-studio/nodes/<category>/<name>)`.

## When to add a page

| The page lets a reader… | Add it to |
| --- | --- |
| Solve one specific problem | `how-to/` |
| Learn a concept once | `concepts/` |
| Look up a fact | the node reference |
| Contribute to the project | `contributing/` |

Do not add a page for internal architecture notes, for anything that changes often, or for an announcement. Put architecture notes in the repo's `docs/` folder, link to external docs instead of copying them, and announce releases in the GitHub release notes.

## Publishing

A docs change is a normal pull request. Run `bun run dev` and check the page before you open it.
