## Set up before you record

- Use the **desktop app**. Broker configuration is desktop-only; the browser build shows a warning instead.
- Have a working public test broker URL and a locally running Mosquitto ready, so you can show both.
- No existing brokers configured — the list starts empty.

## Script

### 0:00 — What a broker is for

**Screen:** Diagram: Studio, the Figma plugin, and a phone, all pointing at one broker in the middle.

**Narration:**
> "A broker is a post office. A sender hands over a message with a topic on the front, like studio slash light-level. A receiver tells the broker which topics it wants. Neither needs to know where the other is. That is how Studio gets a sensor reading into Figma."

### 0:45 — Add a broker

**Screen:** Sidebar → **Configuration** → **MQTT**. The broker list is empty. Click to add. Fill in **Name** `Test broker`, **URL** `wss://broker.example.com:8883/mqtt`, leave username and password empty. Submit. The success toast appears and the broker joins the list.

**Narration:**
> "Configuration, then MQTT. Add a broker. The name is only for you. The URL matters: it must be a WebSocket URL, so `wss` at the front, not `mqtt`. Username and password depend on your broker. Save it, and every flow can use it."

**On-screen text:** `wss://host:port/mqtt`

### 1:30 — Deliberate failure: the wrong scheme

**Screen:** Edit the broker and change `wss://` to `mqtt://`. Save. Show the connection failing — the status never becomes healthy. Hold for five seconds. Then change it back and show it recovering.

**Narration:**
> "This is the common mistake. Most broker documentation gives an address starting with `mqtt` and a port like one-eight-eight-three. That is the address for a native client, and Studio cannot use it. Studio speaks MQTT over WebSockets. Use the broker's WebSocket port. If its documentation never mentions WebSockets, that broker does not work here."

**On-screen text:** `mqtt://… ✗   wss://… ✓`

### 2:15 — Prove it with the test client

**Screen:** Scroll to the **Test Client** card on the same page. Subscribe to `test/#`. Then publish a message to `test/message` with a short payload. The message appears in the subscription list.

**Narration:**
> "Do not build a flow to test a broker. There is a test client here. Subscribe to test slash hash: the hash means everything below this. Publish something to test slash message. If it comes back, the broker works, and any later problem is in your flow. If it does not, fix the broker first."

**On-screen text:** `subscribe test/#  ·  publish test/message`

### 3:15 — Use it from a node

**Screen:** Back on the canvas. Add an **MQTT** node. Open its settings: pick the broker from the dropdown, set a topic, choose direction. Publish from the test client and watch the node's value update.

**Narration:**
> "Now the node. Select the broker you added, set the topic, and choose whether the node subscribes or publishes. Publish from the test client, and the node's value changes on the canvas. That is the same path the Figma bridge uses."

### 3:50 — Public versus your own

**Screen:** The broker list, with a public test broker and a local Mosquitto side by side.

**Narration:**
> "One warning about public test brokers. They are public: anyone can read your topics and anyone can write to them. Use one for a demo, not for anything you care about. Running your own takes about five minutes, and the guide under this video covers it."

## Deliberate failure

The `mqtt://` scheme at 1:30. Show the real failure state, not a mock-up.

## Post-production notes

- Never show a real broker password. Use an unauthenticated broker for the recording.
- The example host must be one you control or a documented test broker — do not point viewers at a stranger's server.
- Caption both URL forms exactly; the difference between them is the whole section.
