title: MQTT will not connect
description: Studio or a bridge plugin never reaches a connected state, or connects and nothing arrives.

Two very different problems wear the same clothes here. Work out which one you have first — it saves an hour.

- **The connection never comes up.** Start at [The connection fails](#the-connection-fails).
- **Both ends say connected, but no values arrive.** Skip to [Connected, but nothing arrives](#connected-but-nothing-arrives). This is the more common of the two, and none of the connection checks will help you.

## The connection fails

### 1. The URL is not a WebSocket URL

This is the most common cause by a distance. Microflow speaks **MQTT over WebSockets** — nothing else.

- Accepted: `wss://host:port/path` and `ws://host:port/path`.
- Not accepted: `mqtt://`, `mqtts://`, or `tcp://`.

Most broker documentation gives you the native address — `mqtt://host:1883` — because that is what a native client uses. You need the broker's **WebSocket** port instead. If a broker's documentation does not mention WebSockets at all, it will not work with Microflow.

If you leave parts out, Studio fills them in: protocol `wss`, port `8883`, path `/mqtt`. So `broker.example.com` becomes `wss://broker.example.com:8883/mqtt` — which is only right if that is genuinely where your broker listens.

### 2. Credentials

If the broker requires a username and password, both ends need them, spelled identically. Brokers rarely report a bad password as anything more specific than a failed connection.

### 3. Prove the broker with the test client

Do not build a flow to find out whether a broker works. Open **Configuration → MQTT** in the desktop app and use the **Test Client** at the bottom of the page:

1. Subscribe to `test/#`.
2. Publish anything to `test/message`.
3. If it comes back, the broker is fine and the fault is downstream. If it does not, stop and fix the broker.

### 4. Your network is blocking it

Institutional and corporate networks commonly block outbound ports other than 80 and 443.

- Try the same broker from a phone hotspot. Works there, fails on the office Wi-Fi? The network is the cause.
- Fix: use a broker that serves WebSockets on 443, or run one locally.

### 5. The broker itself

For a self-hosted broker:

```sh
ps aux | grep mosquitto          # is it running?
nc -zv broker.example.com 8883   # is the port reachable?
```

A Mosquitto install serves native MQTT only until you explicitly add a WebSocket listener. See [Run your own MQTT broker](/docs/how-to/run-your-own-mqtt-broker).

## Connected, but nothing arrives

Both ends healthy, no errors anywhere, and no values. Almost always one of these three.

### 1. The unique identifiers do not match

Every message Microflow sends is addressed under your **unique identifier**:

```
microflow/<unique-id>/figma/variable/<variable-id>
```

If Studio uses `workshop-01` and the plugin uses `Workshop-01`, both are connected to the broker, both are perfectly healthy, and neither will ever hear the other. It is case sensitive, and there is no error for this — it is indistinguishable from a broken sensor.

Check both ends character by character. This is the first thing to check, every time.

### 2. The plugin is closed

A Figma or Penpot plugin only runs while its panel is open. Close the panel and the bridge stops, silently. Reopen it.

### 3. The node is bound to a different variable

Variables are addressed by their **ID**, not their name — so renaming a variable in Figma does not break anything, but deleting and recreating one does, even with the same name. Reopen the node's settings and pick the variable again from the list.

If the variable list in the node's settings is empty, the plugin is not reachable — go back to the identifier check.

## Restart order

When you want to clear stale state, do it in this order:

1. Close and reopen the plugin panel in Figma or Penpot.
2. Reopen the flow in Studio.
3. Quit and reopen Studio.
