---
title: Flow stops mid-run
description: The flow worked, then values stopped. Causes and recovery.
---

A flow that ran fine for a while suddenly stops responding — Monitors freeze, hardware sits still, but the board status in the sidebar is still green. This is rare but worth diagnosing carefully because the cause varies.

## Step 1 — Distinguish "frozen" from "still running but boring"

Before assuming the flow froze, make sure something *should* have changed.

- Does the flow have a [Generate](/docs/microflow-studio/nodes/generate) node (Interval, Oscillator, Trigger, Constant)? If not, the only way values flow is when a Sense input changes — and your sensor may simply not be producing new data.
- Push a button, twist a knob, breathe on a temperature sensor. If a Monitor reacts, the flow is fine.

## Step 2 — Check the connection state

Look at the board status in the sidebar.

- **Green, with the port name** — the connection is still live.
- **No microcontroller connected**, **Connect board** or **Error** — the USB connection dropped. Re-plug the board and Studio reconnects on its own. If the browser does not, click **Connect board**.
- **Error** with *"The flow engine stopped: …"* (browser) — the flow engine itself crashed. Studio switched the board's outputs off and closed the connection. Reload the page to start again. If it happens again with the same flow, please [report it](https://github.com/xiduzo/microflow/issues).

USB drops happen with marginal cables, USB hubs, or when something on your computer aggressively suspends devices.

A board that resets while the cable stays in (a power dip, the reset button) does not drop the connection. Studio sets the board up again and the flow carries on. If it keeps resetting, see [The board keeps resetting](/docs/troubleshooting/node-badges#the-board-keeps-resetting).

## Step 3 — Look for a badge on a node

A node that cannot run shows a red or amber icon in its header. Hover it to read why.

- **"Paused: this node is in a loop that never settles …"** — nodes wired in a circle kept triggering each other. Studio paused them so the rest of the flow keeps running. Change one edge in the loop and they resume.
- **"The board keeps resetting, so this output is held off …"** — a motor, relay or LED strip on the board's 5 V pin is resetting the board.

See [Node badges](/docs/troubleshooting/node-badges) for every message.

## Step 4 — The desktop app restarted the flow

If the desktop app shows *"The flow runtime crashed and was restarted"*, the flow engine hit a bug. Studio switched the board's outputs off, started a fresh engine and loaded your flow into it again. The flow keeps running; outputs come back as the flow drives them.

If the engine crashes three times within a minute, Studio stops it and shows *"The flow runtime keeps crashing, so it was stopped"*. The board is not driven until you click **Reload**. Something in the flow keeps triggering the bug: undo your last change, then [report it](https://github.com/xiduzo/microflow/issues).

The browser has no automatic restart. When the flow engine stops there, reload the page.

## Step 5 — A specific node hung

The most common cause of a flow that stops in the middle is a [Function](/docs/microflow-studio/nodes/shape/function) node whose user code has an issue. The runtime guards against infinite loops (10,000 iteration cap), but slow code can still stall a chain.

- Drop a [Monitor](/docs/microflow-studio/nodes/internal/monitor) just *before* and just *after* every Function node.
- If a Function's input changes but its output never updates, the code inside is the suspect. Look for: large recursive operations, loops over big arrays, accidental string operations on huge data.

If a Function node throws an error, the runtime emits the *last successfully computed value* — so a node may appear to be working when it is actually emitting stale data. Check the Studio console for error messages.

## Step 6 — A Stepper or Servo blocking

Stepper motors with high acceleration or large step counts take real time. While they are moving, the flow does not stop, but a *new* command sent to the same Stepper while it is already moving may be queued or dropped depending on the driver. If a Stepper appears to ignore commands, wait for the previous motion to finish.

## Step 7 — Restart the connection

If nothing else explains it:

1. Disconnect the board. In the browser, click the green board status. In the desktop app, unplug the board.
2. Connect it again. In the browser, click **Connect board**. In the desktop app, plug the board back in.
3. The board reconnects, re-flashes if needed, and the flow resumes.

This rebuilds the entire runtime graph and clears any stale state.

## Step 8 — Restart Studio

If the connection won't recover:

1. Quit the Microflow desktop app, or close the browser tab.
2. Unplug the board, count to five, plug it back in.
3. Re-open Studio and the flow.

This is the nuclear option but always works for a wedged runtime. If you have to do this often, that is a bug — please [report it](https://github.com/xiduzo/microflow/issues) with details.
