The board is plugged in and Studio will not connect to it. Work down this page in order — the checks are ordered by how often each one is the cause, not by how interesting it is.

## First, read the status

| Status | What it means |
| --- | --- |
| **No microcontroller connected** | Desktop app: no serial port found. Start at check 1. |
| **Connect board** | Browser: you have not granted permission yet. Click it. See check 5. |
| **Use Chrome/Edge or the desktop app** | Firefox or Safari. There is no workaround — see check 5. |
| **Connecting** | Studio found a port. Give it a few seconds. |
| **Flashing firmware** | Installing firmware. Can take up to a minute. **Do not unplug.** |
| **Error** | The connection failed outright. Work through this page. |

## 1. The cable

Most "broken Arduinos" are cables. Plenty of USB cables carry power and no data, and they are physically identical to ones that do. The board's power light comes on with either kind, so it tells you nothing.

- Try a different cable — ideally one you have used to upload a sketch from the Arduino IDE.
- Plug straight into the computer, not into a hub.
- If the cable came with headphones, a battery pack, or a phone charger, assume it is charge-only until proven otherwise.

## 2. Another program is holding the port

A serial port has one occupant at a time. If something else has it, Studio cannot.

The usual suspects: the Arduino IDE's **Serial Monitor** or plotter, PlatformIO, a `screen` or `minicom` session, and a second copy of Studio — including a second **browser tab**.

- Close them. On Windows, closing the whole Arduino IDE is safer than just the Serial Monitor.
- Unplug and replug the board.

## 3. The driver

Official Arduino boards work out of the box. Cheaper clones use a different USB-to-serial chip — usually CH340 or CP2102 — which needs a driver on Windows and older macOS.

The tell is that **your operating system itself** cannot see the board. If the OS cannot see it, no application can.

- **Windows** — Device Manager → Ports (COM & LPT).
- **macOS** — System Information → USB.
- **Linux** — `ls /dev/tty*` before and after plugging in.

If the board is not listed, install the driver. See [Install board drivers](/docs/how-to/install-board-drivers).

**Windows, CH340 clone, "device not functioning":** if the board *does* appear as *USB-SERIAL CH340 (COM3)* but Studio still fails — and the same board works on macOS — the newest CH340 driver (4.0) is rejecting the clone chip. Downgrade to 3.4. See [CH340 clones and the "device not functioning" error](/docs/how-to/install-board-drivers#ch340-clones-and-the-device-not-functioning-error-windows).

## 4. The board itself

- Plug in a different board. If that one connects, the first board is the problem.
- Open the Arduino IDE and upload **File → Examples → 01.Basics → BareMinimum**. If that fails too — particularly with `avrdude: stk500_recv()` — the board has a bootloader problem and needs hardware-level recovery, which is outside what Studio can do.

## 5. In a browser

Web Serial has rules a desktop app does not.

- **Firefox and Safari do not support it at all.** The sidebar says so. Switch to Chrome, Edge, or Opera, or install the desktop app.
- **Permission is a deliberate act.** If the status says **Connect board**, nothing has been granted. Click it and pick your board in the browser's chooser. Dismissing that chooser leaves you exactly where you started, with no error.
- **Permission is per origin and per device.** Granted on `localhost` does not carry over to the hosted app, or the other way round.
- **One tab only.** A second tab with Studio open cannot take a port the first one holds.
- **Enterprise policy or `chrome://flags` can disable Web Serial**, in which case Studio reports the browser as unsupported even though it normally would not.

A board you have already granted reconnects on its own after that, including after unplugging and replugging.

## 6. Firmware

Studio checks the firmware every time it connects: it probes the board, flashes Microflow's firmware if it is missing, and connects. So a board that has been used for something else — a sketch from the Arduino IDE, another tool — fixes itself on the next connection.

That means **"the firmware is corrupt" is rarely the answer**. If flashing itself is failing, it is nearly always check 1 or check 2 underneath. See [Flash firmware manually](/docs/how-to/flash-firmware-manually) if you want to take over the process yourself.

## 7. Unsupported board

Microflow generates code for **Arduino Uno**, **Arduino Nano**, and **ESP32**. Other boards may connect and may partly work, but the generated sketch and the wiring diagram will be wrong for them, and nothing will warn you.

Check which target the flow is set to — see [Choose a board target](/docs/how-to/choose-a-board-target).

## Still stuck

Open an issue on [GitHub](https://github.com/xiduzo/microflow-t-stack/issues) with:

- Board name, and whether it is genuine or a clone
- Operating system and version
- Studio version, and whether you are in the desktop app or a browser (and which)
- The exact status text in the sidebar
- Whether the Arduino IDE can talk to the same board
- Whether your operating system lists the board as a serial device

That last pair is what separates a Microflow bug from a machine that cannot see the hardware, and it is the first thing anyone will ask.
