# Microflow QA Standards

> Generated by `steer-qa`. Refine as the test strategy evolves — do not regenerate from scratch.

Last updated: 2026-11-19

## Test Strategy

The Rust runtime is tested with `cargo test`. TypeScript has DOM-less unit tests on `bun test` (`bun:test`, no Vitest): Studio (`apps/web`, including the architecture guard) and shared packages, among them `packages/design-bridge`. Every TypeScript app and package with a `check-types` script is type-checked, the Figma and Penpot plugins included, and `oxlint` lints the tree.

The design-tool bridge protocol has one fixture, `packages/design-bridge/fixtures/protocol.json`. The `bun test` suite of `packages/design-bridge` and the `design_bridge` tests in `crates/microflow-core` both check against it, so a protocol change starts as a fixture change ([ADR-0028](../adr/0028-design-tool-bridge-protocol.md)).

MQTT topic filters have one case table, `packages/design-bridge/fixtures/topic-filter.json`. The one TypeScript `topicMatches`, in `@microflow/design-bridge`, which the plugins and the browser host both route by (`packages/design-bridge/src/topic-filter.test.ts`, `apps/web/src/cloud/topic-filter.test.ts`), and the desktop host's `MqttBroker::topic_matches` (`tests/mqtt_routing.rs`) are all held to it, so a routing change starts as a change to the table.

Tests against a real Firmata board are **not in CI**: the hardware smoke suite (`bun run smoke:hardware` in `apps/web`) is a local gate (see Definition of Done).

## Coverage Requirements

No coverage tool is wired up today, so the rule is **risk-based, not percentage-based**:

- The critical paths must have tests: event routing, board setup and reconnect, wiring, component lifecycle, broker sessions and subscriptions, value sync. (Covered in `crates/microflow-core` beside the code and in `apps/web/src-tauri/tests/*.rs`.)
- Every PR adds at least one test that **would have caught the change breaking** — bug fix, refactor, or new feature. The test grows with the code.
- When a coverage tool is added (likely `cargo-llvm-cov`), the threshold will be set against the snapshot at that moment.

## Test Patterns

- **Location:** Rust unit tests beside the code they cover. Desktop integration tests in `apps/web/src-tauri/tests/<name>.rs`, shared helpers in `apps/web/src-tauri/tests/support/` (`fake_broker.rs`).
- **Naming:** one file per behavior cluster (`mqtt_pool.rs`, `flow_update.rs`, `catalog_parity.rs`, …). Test names describe observable behavior, not method names.
- **Test doubles:** stay at a seam that has a second adapter. The Sim board (`SimBoard`, `SimRig`) instead of a real serial port; `RecordingMqttBrokers` instead of a live broker pool; a modelled bootloader (`SimBootloader`) instead of a board to flash. Do not mock internal runtime types (`FlowRuntime`, `FlowRouter`, etc.) — exercise them directly and assert on the returned `Effects`.
- **Errors:** assert against typed `RuntimeError` variants, never on string content.
- **Async:** use `tokio` test runtime; never `block_on` from a sync test.
- **Time:** a test does not assert a duration. Bound how time grows instead: time the work on an input and on a quarter of it, and hold the ratio under a limit (linear is 4, quadratic is 16). Code that waits takes its clock as a seam, so a test runs it on a fake clock (the browser flash executor's `FlashEnv`, the browser CloudPerformer's timers).
- **Database (TS):** import `@microflow/db/testing` and call `useTestDb()` before each test. Do not replace `@microflow/db` or the room server with `mock.module`.
- **Agent CLI (TS):** run code above the Agent CLI Port on `scriptedAgentCli` (`apps/web/src/ai/scripted-agent-cli.ts`), never on a replaced Tauri module.

## Gherkin → Test Mapping

When a Task issue carries Gherkin scenarios:

- Each scenario maps to at least one Rust integration test.
- Test name references the scenario name so a failure points back to the ticket.
- `Given` → setup (build a flow + mocks). `When` → action (`FlowRuntime::dispatch`, bytes fed through a `SimRig`, etc.). `Then` → assertions on the returned `Effects`, the sim board's state or runtime state.
- Scenarios describe observable runtime behavior, not implementation.

## Commands

```bash
# Lint + format (CI gate, TS)
bun run check

# Type check (CI gate, TS — includes both design-tool plugins)
bun run check-types

# TypeScript unit tests (CI gate) — Studio and packages, incl. packages/design-bridge
bun test

# Build the design-tool plugins (CI gate)
bunx turbo build --filter=figma-plugin --filter=penpot-plugin

# Clippy pedantic (CI gate, Rust; from the repo root)
cargo clippy --workspace --all-targets -- -D warnings -W clippy::pedantic

# Run all Rust tests (CI gate; from the repo root)
cargo test --workspace --lib --tests

# Run a single integration test file
cd apps/web/src-tauri && cargo test --test mqtt_pool

# Run the engine's tests (the runtime is not a default feature)
cargo test -p microflow-core --features runtime

# Bless the wire interface, regenerate, then run the Catalog Parity Guard
cd apps/web && bun run catalog:sync

# Hardware smoke suite against a real board (not in CI)
cd apps/web && bun run smoke:hardware

# Benchmarks (not in CI)
cargo bench -p microflow-core --features runtime

# Cross-platform Tauri build (matches build.yml matrix) — local equivalent
cd apps/web && bun run desktop:build
```

## Definition of Done

A Task is ready to merge when **all** of the following are true:

- [ ] `bun run check` passes (oxlint + oxfmt)
- [ ] `bun run check-types` passes
- [ ] `bun test` passes
- [ ] If the design-tool bridge protocol changed: `packages/design-bridge/fixtures/protocol.json` was updated, and both the bun tests and the `microflow-core` tests pass
- [ ] `cargo clippy --workspace --all-targets -- -D warnings -W clippy::pedantic` passes
- [ ] `cargo test --workspace --lib --tests` passes
- [ ] Cross-platform Tauri build passes (build.yml matrix: macOS Intel / ARM, Windows MSVC, Linux x86_64)
- [ ] If `node-components.json`, a node schema, or a node's Rust `ports()` / `emits()` / config changed: `bun run catalog:sync` (in `apps/web`) passed and the generated files (`apps/web/src/nodes/*.generated.ts`, `wire-interface.generated.json`, `node-defaults.generated.json`) are committed
- [ ] If the Task has Gherkin scenarios: each scenario has a corresponding Rust integration test
- [ ] If the change touches hardware code (the board link, the runtime actor's port handling, a `HardwareComponent` impl): `bun run smoke:hardware` against a real Firmata board before merge
- [ ] If the change touches a flash driver or a flash executor: the flash check, once per affected protocol (`MICROFLOW_HW_PORT=… MICROFLOW_HW_FLASH=<board id> bun run smoke:hardware`, from `apps/web`)
- [ ] If domain terms changed or new terms were introduced: `CONTEXT.md` updated
- [ ] If an architectural decision was made: an ADR is added under `docs/adr/NNNN-*.md`
- [ ] Regression test added for any bug fix

## Test Environments

| Environment | Purpose | Access |
| --- | --- | --- |
| Local — no hardware | Run all Rust tests on the Sim board and the recording adapters | `cd apps/web/src-tauri && cargo test` |
| Local — with Firmata board | The hardware smoke suite for hardware-touching changes | Plug a Firmata-flashed board into USB; `cd apps/web && bun run smoke:hardware` (add `MICROFLOW_HW_FLASH=<board id>` to flash it first) |
| Local — DB-backed tests | `@microflow/db`, `@microflow/api` and `@microflow/collab` tests on the in-process Postgres (`@microflow/db/testing`: PGlite with the real migrations) | `bun test`; no Docker, network or environment |
| Local — server | Run `apps/server` against a real Postgres | `bun run db:start` (docker compose), `bun run db:push`, then `bun run dev` |
| CI — Rust | Clippy + test gate on PR to `main` | `.github/workflows/rust.yml` |
| CI — TypeScript | `bun test` + `oxlint` (test job); `check-types` + a build of the Figma and Penpot plugins (check-types job), on PR to `main` | `.github/workflows/typescript.yml` |
| CI — Build | Cross-platform Tauri build on PR to `main` | `.github/workflows/build.yml` |
| CI — Release | Signed release artifacts | `.github/workflows/release.yml` on `v*` tag |

## Known Flaky Areas

- **Broker pool tests over TCP.** `tests/mqtt_pool.rs` runs the desktop pool against an in-process fake broker over loopback. When a failure in this file appears once and disappears on rerun, file a ticket rather than ignoring — repeated single-shot failures are a real signal.
